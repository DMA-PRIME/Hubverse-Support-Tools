    GitHub from zero

    First, understand where your submission goes

    You are not placing a file directly into someone else’s repository. You make a personal copy, work safely in that copy, and then ask the sandbox or hub to review your change.

    You need a personal GitHub account

    A free personal account is enough for the practice workflow. Sign in to the correct account before opening the sandbox. Your username becomes the owner name shown on your fork.

    i

    The guide cannot sign you in. Account creation, security verification, and every repository action happen on GitHub after the sandbox is published.

    How do I know I am signed in?

    GitHub shows your profile picture or account menu in the upper-right corner. Open it and confirm the displayed username is yours before you fork anything.

    1Repository

    The project’s online folder. The original sandbox belongs to DMAPRIME and contains instructions, examples, and automated checks.

    2Fork

    Your GitHub-hosted copy of that repository. You own this copy, so practice changes there do not alter the original.

    3Branch

    A named workspace inside a repository for one change. Use one new branch for each submission attempt.

    4Commit

    A saved snapshot of selected changes. A commit records files and a short explanation; it does not request review yet.

    5Pull request

    A request to compare your branch with the original repository and consider bringing in those changes.

    6Checks

    Automated tests attached to the pull request. Green means those tests passed; it does not automatically mean the hub accepted the submission.

    The most important distinction: original repository versus your fork

    The files may initially look identical. Read the owner name at the top of the page to know which copy you are viewing.

    Exactly what “fork the repository” means

    Open the original sandbox page

    Check that the owner shown before the slash is DMAPRIME. Do not start from another student’s fork.

    Select Fork near the upper-right corner

    If GitHub asks you to sign in, sign in and return to the original repository page.

    Choose yourself as the owner

    On “Create a new fork,” choose your personal username. Keep the repository name unchanged.

    Keep only the default branch

    For this practice submission, leave “Copy the main branch only” selected when GitHub offers that choice.

    Select Create fork and wait

    GitHub creates the copy and opens it. This may take a moment; do not refresh repeatedly.

    Verify where you landed

    The page should show YOUR-USERNAME/hubverse-submission-sandbox and a note such as forked from DMAPRIME/hubverse-submission-sandbox.

    Later, your pull request will mean:
    Please compare MY fork’s submission branch with DMAPRIME’s main branch.

    Hub-specific quick reference

    Know the rules that change

    This is an orientation, not a replacement for the active challenge instructions.

    Which upload route fits the file?

    GitHub's general per-file thresholds are shown below. A hub can impose stricter rules.

    0–25 MiB
    Browser    25–100 MiB
    Desktop / Git    Over 100 MiB
    Stop & check
    !

    Do not assume Git LFS is allowed. For a file over 100 MiB, use the hub's approved compression or partitioning method, or contact its administrators.

    First submission

    Include model metadata in the exact path shown by this guide, and confirm any hub-specific registration or authorization requirement in the active instructions.

    Repeat submission

    Sync your fork or local clone before starting. Put only the new output—and a metadata update only when needed—on a fresh branch.

    Correcting an open pull request

    Keep the pull request open. Replace the file on the same branch, commit, and push again. The existing pull request updates automatically and checks rerun.

    After the deadline

    Do not silently replace files or open a late pull request. Follow the hub's documented late-submission policy.

    Definition of done

    Do not stop at “Create pull request”

    A green, merged submission is the goal. Use this list before you close the browser.

    When something goes wrong

    Most red checks are fixable clues

    Read the first useful error

    “File path / name is invalid”

    Check the parent folder, team-model spelling, date, hyphens versus underscores, and extension. The folder and filename must use the exact model identifier registered with the hub.

    “Unexpected or missing columns”

    Compare column names with the active round's task configuration or model-output README. Extra spreadsheet index columns such as Unnamed: 0 commonly cause this.

    “Value or output type is invalid”

    Check allowed targets, horizons, locations, output types, quantile levels, missing-value encoding, and whether numeric columns were exported as text.

    “Merge conflict” or branch behind

    Sync the fork, update the branch from the hub's default branch, resolve only your file if possible, then push the updated branch. Ask for help before guessing on a conflict in hub-maintained files.

    Use the pull request conversation

    The Checks tab tells you what the automation ran. The Conversation tab is where maintainers explain warnings or request changes.

    ✓

    Green checks: the automated rules passed. You may still need a human review or merge.

    !

    Warning: read it. Some hubs permit documented warnings; others require changes.

    ×

    Red check: open the failed check, expand the log, correct the named problem, and update the same branch.

    Plain-language glossary

    GitHub words, translated

    Repository
    The project folder on GitHub: files, history, instructions, and automated checks.
    Fork
    Your GitHub copy of someone else's repository. You can safely propose changes from it.
    Clone
    A repository copied from GitHub onto your computer.
    Branch
    A named workspace for one change. It keeps your submission separate from the main version.
    Commit
    A saved snapshot with a short message explaining what changed.
    Push
    Send local commits from your computer to GitHub.
    Pull request (PR)
    A proposal to bring the changes on your branch into the hub repository.
    Upstream
    The original hub repository from which your fork was made.
    GitHub Actions
    Automated jobs that validate filenames, file contents, timing, and other rules.
